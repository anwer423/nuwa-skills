# 技能规范（skill-spec）

## 目录结构

```
skill-name/            # 目录名 = frontmatter 里的 name
├── SKILL.md           # 必需
├── scripts/           # 可选：可执行代码
├── references/        # 可选：按需加载的长文材料
└── assets/            # 可选：进产出的模板/素材
```

技能目录里只放跑得起来的文件和真正要被读的内容。README、安装指南、更新日志一律不进去。

## SKILL.md

### frontmatter

```yaml
---
name: pdf-tools
description: 一句话说清做什么 + 什么时候用（含触发词）
---
```

- 只允许 `name`、`description`。多写的字段不但无效，还会让解析器困惑。
- `name`：kebab-case，字符集 `[a-z0-9-]`，不能有连续或首尾连字符，必须等于目录名。
- `description`：这是唯一的触发器，写得像搜索关键词而不是广告词。要含用户可能说的原话（「转成 PDF」「提取文字」「表单填写」）。
- 长度经验值：中文 60–300 字。太短触发不准，太长挤占上下文。

### 正文

- 祈使句，直接给动作和判据，不写背景故事。
- 500 行以内。逼近上限就拆 `references/`。
- 不写「何时使用本技能」章节——那部分在上面的 description 里已经完成。
- 不写「本技能由谁创建、怎么测试」之类的过程信息。

## 渐进式披露

三级加载：metadata（始终在上下文）→ SKILL.md 正文（触发后加载）→ 附带资源（需要时读）。

推论：
- 高频必需的信息放 SKILL.md；低频大块材料放 references。
- references 里超过 100 行的文件加个目录，方便先看全貌再局部读。
- 同一信息只在一个地方写，不要在 SKILL.md 和 references 里各抄一遍。

## 组织方式

- 按领域拆：`references/finance.md`、`references/sales.md`，所需即所读。
- 按变体拆：`references/aws.md`、`references/gcp.md`，用户选了云厂商才读对应文件。
- 按深浅拆：基础用法写在 SKILL.md，高级用法单独成文并给入口。

## 常见反模式

| 反模式 | 表现 | 后果 |
| --- | --- | --- |
| 说明书化 | 大段介绍技能来历、优势、原理 | 白烧上下文，AI 不需要 |
| 万能包 | 一个技能塞进搜索、写作、发邮件、对账 | 触发混乱，执行时读一堆无关内容 |
| 示例垃圾 | 初始化模板留下的 example.py 没删 | 误触发、误导执行 |
| 双份文档 | SKILL.md 和 references 内容重复 | 改一处忘一处，行为不一致 |
| 隐形引用 | 提到某个文件却不说什么时候读 | 该读的时候没读，行为退化 |
| 无脚本硬讲 | 用文字描述一大段本可固化的代码逻辑 | 每次都重写，结果不稳定 |
