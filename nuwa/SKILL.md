# 女娲（Nuwa）

女娲负责造技能：输入是人的经验（一次跑通的对话、一份 SOP、一套操作步骤），输出是一个能直接装进 `.skills` 或 `workspace/.user_skills` 里被调用的 Skill 目录。

## 心法

- 技能是写给「另一个 AI」的，不是给人看的说明书。它推理能力已经够用，只缺它自己想不到的东西：口径、私有路径、踩过的坑、判断标准、可直接执行的脚本。
- 每一条都要过一遍「值多少 token」。删掉不影响执行的一律删。
- 一个技能只解决一类事。两件事就拆两个技能，别做万能包。

## 流程

### 1. 采：拿到真实素材

至少要有一样：用户口述的操作步骤、一次成功任务的记录、已有文档或现成脚本。素材只有一句「帮我做成技能」时，先追问三件事——什么场景触发它、上次具体怎么做的、哪一步最容易出错。不要凭空编流程。

### 2. 判：值不值得做成技能

以下同时成立才继续：会重复发生（大致每月数次以上）；步骤稳定；含 AI 自己想不到的知识（口径、私有路径、踩坑）；或者每次都要重写同一段代码。
不成立就直接说「不值得做成技能」，并给更轻的替代方案：写进记忆、做成模板、单文件脚本。

### 3. 定自由度

- 靠判断、多路径都能走通 → 文字指令（高自由度）
- 有固定套路但参数会变 → 伪代码或带参脚本（中自由度）
- 顺序不能错、一步错全错 → 写死脚本 + 明确参数（低自由度）

### 4. 拆：三件套

- `scripts/`：要反复重写、要求确定性、逻辑偏长的部分 → 固化成脚本
- `references/`：口径表、字段定义、接口规范、判定标准、长案例 → 按需加载
- `assets/`：要直接进产出的模板、图片、字体、样板文件

原则：SKILL.md 只留流程与取舍，长材料挪进 `references/`，并在 SKILL.md 里写清「什么时候读哪个文件」。引用只做一层，别链式中转。

### 5. 写：SKILL.md

- frontmatter 只允许 `name` 和 `description` 两个字段。description 必须同时写清「做什么」和「什么时候用」，触发词全部放这里；正文里再写「何时使用」是浪费。
- `name` 用 kebab-case，必须和目录名一致。
- 正文用祈使句，控制在 500 行以内。示例优先于解释。
- 不留待办标记、占位符、示例垃圾文件，也不要在技能目录里放 README、CHANGELOG 之类的说明文档——文档放仓库根目录，不要放技能目录。

### 6. 验：跑校验再交付

```bash
python scripts/validate_skill.py <skill-dir>
```

校验覆盖：frontmatter 字段与命名规范、description 质量、正文长度、内部引用文件是否存在、脚本语法、TODO 残留、多余文档文件。有 error 必须修完才能交付；warning 逐条确认是否可接受。

`scripts/` 里的脚本必须真跑一遍，没跑过就是猜的。最后照 `references/quality-gates.md` 逐条过验收清单。

## 附带资源

- `references/skill-spec.md` — 目录结构、frontmatter 规则、渐进式披露、常见反模式
- `references/quality-gates.md` — 交付前验收清单（逐条勾）
- `scripts/init_skill.py` — 生成符合规范的技能骨架
- `scripts/validate_skill.py` — 结构与规范校验器
